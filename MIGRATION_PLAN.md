# COBOL Banking System Modernization Plan

## Active Goal

Modernize `BANKACCT.cob` into a maintainable target-stack application that faithfully reproduces the COBOL banking behavior, using the simulator only as non-authoritative reference.

## Scope

- Source of truth: `BANKACCT.cob`
- Legacy data files: `CUSTOMERS.DAT`, `TRANSACTIONS.DAT`
- Excluded from modernization target: the Python simulator generated by `setup.sh`
- Intended outcome: a modern application that runs independently and reproduces the COBOL program's banking behavior

## Selected Target Stack

- Runtime: Python 3
- Persistence: SQLite
- Core verification: pytest and coverage.py
- Interface: independent CLI plus an optional FastAPI adapter
- Dependency posture: core behavior and migration run without installing FastAPI or invoking the simulator

## Simplified Seven-Step Migration Plan

### 1. Discovery and Diagnosis

- Treat `BANKACCT.cob` as the authoritative legacy system.
- Map COBOL divisions, paragraphs, file definitions, data records, and business rules.
- Document data layouts for customer and transaction records.
- Identify mismatches between `BANKACCT.cob`, README documentation, sample data, and simulator behavior.
- Record modernization assumptions and exclusions.

### 2. Prioritize and Re-architect

- Choose the target technology stack.
- Define domain boundaries:
  - Accounts
  - Transactions
  - Mini statements
  - Interest calculation
  - Data migration
- Decide the target architecture, persistence model, and delivery slices.
- Prioritize behavior-preserving migration before feature expansion.

### 3. Slice and Refine

- Convert COBOL paragraphs into functional mappings.
- Define acceptance scenarios for each behavior slice.
- Simplify process flow only where simplification does not change intended behavior.
- Capture product and process gaps before deciding whether to preserve, remove, or redesign them.

### 4. Build and Transform

- Set up the modern application structure, test framework, and development commands.
- Rebuild the banking behavior incrementally in the target stack.
- Start with domain logic, then persistence, then API or CLI interfaces.
- Keep each migrated slice behavior-equivalent to the COBOL baseline.

### 5. Clean and Migrate Data

- Design the target data model.
- Map fixed-width COBOL records into the target schema.
- Build import or migration tooling for `CUSTOMERS.DAT` and `TRANSACTIONS.DAT`.
- Validate migrated balances, account types, and transaction history.

### 6. Test and Iterate

- Create characterization tests from `BANKACCT.cob` behavior.
- Add unit tests for business rules.
- Add integration tests for persistence and migration.
- Run end-to-end scenarios comparing legacy and modern outputs.
- Iterate until behavior parity is proven for agreed scenarios.

### 7. Deploy and Maintain

- Document how to run, test, and extend the modernized system.
- Record non-obvious architecture decisions in `DECISIONS.md`.
- Update README after the target stack and commands are stable.
- Leave clear maintenance notes for future agents and developers.

## Verification Standard

The modernization is complete only when the modern implementation can run independently, reproduce agreed COBOL banking scenarios, migrate legacy data, and pass automated verification without relying on the simulator as the source of truth.

## Numeric Success Targets

Use these targets to make verification objective:

- COBOL inventory coverage: 100% of `BANKACCT.cob` divisions, file records, working-storage fields, and procedure paragraphs are mapped before implementation starts.
- Behavior scenario coverage: at least 8 legacy behavior scenarios are documented and automated:
  - Create account
  - View accounts
  - Deposit
  - Withdrawal
  - Insufficient funds
  - Missing account
  - Mini statement
  - Savings interest
- Behavior parity: 100% of agreed characterization scenarios pass against the modern implementation.
- Data migration coverage: 100% of valid rows in `CUSTOMERS.DAT` and `TRANSACTIONS.DAT` are imported or explicitly rejected with a documented validation reason.
- Balance accuracy: migrated and computed balances match COBOL behavior to the cent for every tested scenario.
- Transaction accuracy: transaction count, account ID, type, amount, date, and time fields match the expected COBOL record interpretation for every migrated transaction.
- Automated test target: at least 90% line coverage for the new domain and data migration code.
- Independent run target: the modernized application starts, runs the end-to-end scenario suite, and passes without invoking `setup.sh`, `cobc`, or the generated simulator.
- Documentation target: README, `DECISIONS.md`, and this migration plan describe the final run commands, architecture, verification commands, and known exclusions before the migration is marked complete.
